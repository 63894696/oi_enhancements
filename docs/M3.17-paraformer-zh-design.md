## 1. 现状(2026-09-17 复查)

`companion/companion_asr_providers.py:509-528` 已经注册了 `local-funasr` spec,model 选项包括:
- `auto`(由 funasr-websocket server 端决定)
- `paraformer-zh`(FunASR-Paraformer-Large, 220M)
- `sherpa-onnx-paraformer-zh`(220M,轻量)
- `sensevoice-small`
- `llama-funasr-q4`

端点默认 `ws://127.0.0.1:10095/`,模式 `2pass`(边识别边出句)。

云端主用 `bailian-paraformer-v2`(WebSocket 流式,中文 CER 3.40%)。

## 2. Paraformer-zh 可选部署路线对比

### 路线 A:FunASR 原版(Docker runtime SDK)
- **来源**:阿里达摩院 FunASR 主仓 `registry.cn-hangzhou.aliyuncs.com/funasr_repo/funasr:funasr-runtime-sdk-online-cpu-0.1.12`
- **模型**:Paraformer-zh-streaming 220M
- **接口**:WebSocket 流式(modes: 2pass-online/offline, partial/final)
- **跑法**:`docker run -p 10095:10095 <image> --model paraformer-zh`
- **依赖**:Docker Desktop 已装(用户机器上有)
- **CPU/GPU**:CPU 镜像与 GPU 镜像分开
- **RTF**:README 没给,FunASR 官方 `docs/benchmark/rtf_reproducibility.md` 让用户自测
- **风险**:镜像要从阿里云杭州 registry 拉(国内用户可,海外可能慢);护线 / WSL2 / 火绒可能拦 docker 网络
- **优点**:官方原版,精度有保证(220M Large)

### 路线 B:sherpa-onnx Paraformer-zh
- **来源**:k2-fsa/sherpa-onnx prebuilt 镜像
- **模型**:`sherpa-onnx-paraformer-zh-2024-03-09.tar.bz2`(中英)
- **接口**:**仓库本身没统一 WebSocket server 命令**,只有第三方 Go/C++ 实现(asr_server / stt-server / voiceapi)
- **Python**:直接 `import sherpa_onnx`,跑同步识别,不直接走 WebSocket
- **RTF**:CPU 上常见报告 0.1-0.3(纯 Paraformer-zh,单核)
- **优点**:零依赖 ONNX runtime,模型小(< 200MB),CPU 实时
- **风险**:**起 WebSocket server 要自己写一个薄层**(或用第三方),这是接入现有 `local-funasr` spec 的最大摩擦点

### 路线 C:llama-funasr(gguf 自包含二进制)
- FunASR 主仓最近加的「single self-contained binary on CPU/edge」路径
- 命令:类似 `llama-funasr --model paraformer-zh-streaming-q4`
- **优点**:单文件,无 Python 依赖
- **缺点**:版本新,文档稀,生产参考少

### 路线 D:SenseVoice-Small(非 Paraformer)
- 70M 参数,比 Paraformer 小 3 倍,多语言(中英日韩)
- 适合「快糙猛」场景,精度略低于 Paraformer-zh
- 适合「兑底通道」:本地 SenseVoice 不准时切换到云端 Paraformer-v2

## 3. 推荐路线:**A 主用 + D 兑底**

理由:
- **A 主用**:Docker 一行命令,接口跟现有 `local-funasr` WebSocket 完全对齐(mode 2pass-online/offline + partial/final + ready/finished),接入零代码
- **D 兑底**:如果 A 没装 Docker / 镜像拉不下来,降级到 SenseVoice-Small(更轻量更稳)

e2e 路径:
1. `docker run -d --name funasr -p 10095:10095 registry.cn-hangzhou.aliyuncs.com/funasr_repo/funasr:funasr-runtime-sdk-online-cpu-0.1.12` — 启服务
2. `companion_asr_providers` 把 active_provider 改 `local-funasr`,model 选 `auto`
3. 麦克风流式说话,看 `on_partial` / `on_final` 触发
4. 跟 `bailian-paraformer-v2` 比较 CER(可以用已有的 audio_voice_eval 跑一遍)

火绒白名单可能要加 docker / python.exe 子进程路径;WSL2 网络要 NAT 打通 10095。

## 4. 知识库兜底通道设计

### 4a. 本地 ASR 失败的常见情形
- Docker 没起 / 镜像被删 / 10095 端口被占
- CPU 推理 RTF > 1(说话比识别慢,出现「积压」)
- mic 静音被误判成有效语音(`finalize=true` 出空文本)
- 离线缓存拉不到 VAD 模型

### 4b. 兜底策略(三选一)

**策略 1:无感切换(本地 ASR 故障 → 自动跳云端)**
- `companion_asr.py` 加 `active_provider` 回退链:`[local-funasr, bailian-paraformer-v2]`
- 触发条件:5 秒内没收到 partial/final、连接异常、连续 3 个空 final
- UI 显示「本地 ASR 不可用,已切换到云端」(一次性 toast)
- **缺点**:用户隐私优先的承诺被破坏,云端是有声音流出的
- **适用**:用户明确允许的场景(比如「非隐私模式」开关)

**策略 2:硬失败 + 提示手动切换**
- 本地 ASR 故障就弹窗「本地 Paraformer 未启动,请起服务或手动切换到云端」
- 不静默切换,尊重用户隐私设置
- 适配 `companion_asr_providers` 已经有 provider dropdown UI,用户改一下就行
- **缺点**:用户要手动操作,慢

**策略 3:并行跑(本地 + 云端,取信置信度高者)**
- 同一段 mic 音频,同时送本地 + 云端
- 比较 final 文本相似度(编辑距离 < 阈值 → 同,> 阈值 → 标差异,UI 让用户挑)
- **优点**:不损失隐私(本地为主),云端做对账
- **缺点**:双倍流量 / 双倍费用;云端 KEY 必须有

### 4c. 推荐:策略 2(默认)+ 策略 1(可选)

- 默认走策略 2(尊重隐私 + 现有 UI 兼容)
- 用户在 settings 加一个「允许 ASR 联网兑底」开关
  - OFF → 策略 2(只本地,故障弹窗)
  - ON → 策略 1(本地故障无感切云端,UI toast 告知)
- 策略 3 作为 1.5 期路线(需双 KEY + 相似度计算)
