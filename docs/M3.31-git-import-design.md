# M3.31 设计方案 — 外部版本管理兼容(git 子集) + 同 LAN 多 agent 协作扩展性(2026-09-16)

## 0. 用户确认的设计原则(2026-09-16 复盘)
1. **同源同栈 + git 子集(最广兼容)**:PrisirAI snapshot + 任何「内容寻址 + ts 后缀 + sidecar」的同类工具 + .git/objects 里 HEAD blob
2. **静默忽略不打扰**,除非用户**主动把目录设为工作区**,且 agent 已经**读过该文件**(in-memory 有当前内容)
3. **不开放用户手动加入入口** — 只能通过「切 workdir + agent 读过」间接触发格式转换
4. **新需求先出方案,确认后再开发**

---

## 1. 数据流总览

```
[扫描触发条件]
  用户切 workdir 到 git 仓库根
        │
        ▼
[扫描 worker] 后台线程,异步,≤1 次/30s 节流
  walkdir(_WORKDIR) → 命中 .git/ 路径 → 记录 (repo_root, sub_paths)
        │
        ▼
[读取触发条件]
  用户在任一会话里调用 read_file 工具,且 path ∈ 已记录 sub_paths
        │
        ▼
[格式转换 worker] 立即执行(用户操作不能延迟)
  git ls-tree HEAD <path> → blob SHA
  git cat-file -p <blob_sha> → 当前 HEAD 内容(子进程,5ms 级)
  写 .prisir_snapshots/<sha1(path)>/<ts>_imported_<size>B
  写 sidecar <same_sha1>/<ts>_imported_<size>B.meta.json
        │
        ▼
[timeline 可见]
  file_changes 扫到 op:"imported" → 渲染时前缀图标 git-import
  用户可点 → 跳「📄 只读预览」/「📊 版本对比」
```

## 2. 数据结构

### 2.1 Sidecar metadata.json
```json
{
  "imported": true,
  "imported_at": 1758012345.678,
  "origin": "git-import",
  "src_repo": "C:/Users/Administrator/repos/foo.git",
  "src_blob_sha": "a3f5b2c...",
  "src_commit_sha": "e7b1c3f...",
  "src_path": "src/main.rs",
  "size": 4096,
  "tool_who": "agent-call-uuid-xxx"
}
```

### 2.2 Snapshot 命名
沿用现有格式:`<sha1_of_path>/<ts>_<tool>_<size>B`
- `<tool>` 字段:`imported`(本次新增)/`write_file` / `edit_file` / `rollback`
- 后端 `prisir_snapshot.list_versions(abs_p)` 不用改,只看 ts+size+tool

### 2.3 排除标记(防重复导入)
sidecar 里 `imported:true` + 同时在 `_WORKDIR/.prisir_snapshots/.imported_index.json` 加全局索引:
```json
{
  "C:/Users/Administrator/repos/foo/src/main.rs": {
    "snapshot_ts": 1758012345.678,
    "src_blob_sha": "a3f5b2c...",
    "imported_at": 1758012345.678
  }
}
```
扫描 worker 检查这个索引,跳过已导入的文件。

## 3. 后端新增 4 个 API

### 3.1 `POST /prisiragent/api/git_import_scan`
手动触发扫描(扫描 worker 也自动跑,这是给 e2e 测用的)
- **无 body**,内部从 `_WORKDIR["path"]` 取
- 返回 `{ok, repo_roots: [...], candidates: [{abs_path, src_blob_sha}], skipped_already_imported: [...]}`

### 3.2 `GET /prisiragent/api/git_import_status?path=...`
查单个文件是否已纳入 / 在哪个索引里
- 返回 `{ok, is_imported, snapshot_ts, src_blob_sha, src_commit_sha}`

### 3.3 `POST /prisiragent/api/git_import_now`
手动强制导入一个文件(e2e 用 + debug 兜底)
- body `{path}` → 走转换 worker 立即跑 → 写盘
- 用户界面**不暴露**此 API,只有 e2e 测调用

### 3.4 `GET /prisiragent/api/git_import_list`
列已导入的所有文件(给 timeline 备份路径用)
- 返回 `{ok, items: [{abs_path, snapshot_ts, src_blob_sha, src_commit_sha, src_repo}]}`

## 4. 实现细节

### 4.1 触发器:扫描 worker(后台线程)
- `prisiragent_web.py` 启动时拉起 `_git_import_worker_thread`
- 主循环:`while True: sleep 30s; _git_import_scan_once()`
- `_git_import_scan_once()`:
  - `_WORKDIR["path"]` 改变时强制执行一次
  - walkdir 找 `.git/` 目录,记录 `repo_root`
  - 对每个 repo_root,枚举 sub_paths(只读 git index,不解 commit)
  - 检查 `.imported_index.json`,过滤掉已导入的
  - 把剩余 candidates 缓存到 `_GIT_IMPORT_CANDIDATES` 全局 dict

### 4.2 触发器:读触发器
- 现有 `read_file` 工具实现(`prisiragent_cli.py:??`)在返回 content **之前**,调 `_maybe_git_import(path, content)`
- `_maybe_git_import`:
  - path ∈ `_GIT_IMPORT_CANDIDATES`?
  - 否 → 直接返回
  - 是 → 子进程跑 `git cat-file -p $(git ls-tree HEAD <path> | awk '{print $3}')`
  - 拿到 blob 内容 → 写 snapshot + sidecar + 更新 `.imported_index.json`
  - 整个过程超时 5s,失败静默 log

### 4.3 git 操作:走子进程,不解析 delta
- `git ls-tree HEAD <path>` → 1 行输出 `100644 blob <sha>\t<path>`
- `git cat-file -p <sha>` → 标准输出原始文件内容
- 不读 `.git/objects/pack/*.pack` 直接,避免 delta 解析复杂性
- 性能:5ms × 文件数,scan 时不会阻塞(后台线程);read_file 时单次 5ms 可接受

### 4.4 边界处理
| 场景 | 处理 |
|---|---|
| workdir 没有 git | 扫描无 candidates,什么都不发生 |
| workdir 是 bare repo | 跳过(.git 在根,无 working tree) |
| workdir 是 submodule | 标 `submodule:true`,不入库,只记日志 |
| path 是 symlink | realpath 后再校验 |
| path > 10MB | skip,记 debug log |
| git 命令失败(returncode != 0) | skip,记 warning log,不报错给用户 |
| 工作区切走后又被切回 | 重扫,但 `.imported_index.json` 阻止重复 |

### 4.5 写盘原子性
- snapshot 文件:沿用现有 `prisir_snapshot.snapshot_before_write`,内部已有 atomic rename
- sidecar `.meta.json`:写 `.tmp` → rename
- `.imported_index.json`:加 file lock(`fcntl` Windows 下用 `msvcrt`),改完 release

# 10. 同 LAN 多用户多 agent 协作扩展性讨论

## 10.1 当前 M3.31 完成后,能支持什么

**答:M3.31 完成后,「同一 LAN 内多 agent 写同一文档」的**可行性**已经具备,但「可用性」还差几步。**

### 10.1.1 具备的基础
- **每个 agent 进程都有完整 PrisirAI 链路** — snapshot/rollback/diff 都独立
- **snapshot 是内容寻址的** — sha1(path) → `.prisir_snapshots/<sha1>/...`,多 agent 写同一路径会落到**同一个目录**,只要文件锁得当就能合并

### 10.1.2 关键缺口
| 缺口 | 现状 | 解决方向 |
|---|---|---|
| **进程间通信** | 各 agent 进程独立,不知道对方写什么 | 共享 snapshot 目录(LAN 文件共享 / NFS / 共享 mount) + watch 机制 |
| **冲突检测** | 无 — 两个 agent 同时 write_file 会互相覆盖 | snapshot 写盘用 advisory lock + write_file 工具读 index 判定是否 stale |
| **冲突解决** | 无 — 覆盖后只保留后写者 | last-writer-wins 太粗暴,需要 3-way merge(基于 git import 得到的 blob + 当前新写) |
| **用户感知** | 无 — 没人知道别人在改 | timeline 增加「其他 agent @host 写于 ts」` 事件来源 |

## 10.2 协作模式的两种架构

### A 方案:共享 snapshot 目录(轻量)
```
Host A: agent A 写 .prisir_snapshots/<sha1>/<ts>_write_<size>B
Host B: agent B 同样写 .prisir_snapshots/<sha1>/<ts>_write_<size>B
   ↓
两者共享同一个 mount(LAN/SMB/NFS)
   ↓
file_changes 合并两个 host 的事件,timeline 显示两个来源
```
**优点**:改动小,M3.31 完成后即可
**缺点**:写锁弱(网络文件系统 advisory lock 不可靠);无实时通知;rollback 跨 host 行为不一致

### B 方案:加一个轻量协调服务(重量,推荐后续做)
```
[Agent A] ─┐
[Agent B] ─┤── HTTP ──→ [Coordinator] ←── HTTP ── [Agent C]
                              │
                              └── 维护:
                                   - file_locks: {abs_path → owner_host + ts}
                                   - version_vector: {abs_path → {host: ts}}
                                   - peer_registry: {host → last_heartbeat}
```
**优点**:有锁、有冲突检测、有实时通知
**缺点**:多了个服务要部署 + 高可用;M3.31 不包含

## 10.3 推荐路线

| 阶段 | 内容 | 工作量 |
|---|---|---|
| **M3.31 (现在)** | 单 agent + git import | 5-7h |
| **M3.32 (下一步)** | 共享 snapshot 目录 + 跨进程 file_changes merge + timeline 显示 host 标签 | 4-6h |
| **M3.33 (再下一步)** | Coordinator 服务(版本向量 + 锁) | 8-12h |
| **M3.34 (远期)** | 3-way merge UI + 实时通知 | 10+h |

## 10.4 关于「是否能扩展支持」的明确回答

- **M3.31 完成后**:架构上**可以**走 A 方案(共享 mount),但用户体验上是「事后看 timeline」,不是「实时协同」
- **想做到实时协同(多人同时改同一段不冲突)**:必须做 B 方案的 Coordinator 服务,这是 M3.33 的工作
- **不会做自动 merge(全自动 3-way merge)**:有不确定性风险,推荐让 agent 把冲突暴露给人类(类似 git merge conflict),由人或高阶 agent 解决

## 12. 用户决策(2026-09-16)

1. **git 命令依赖**:✅ OK,Windows/Linux/macOS 默认有 `git`,无额外依赖
2. **文件大小限制**:**取消 10MB 硬上限**。改为跟随版本管理工具自身上限:
   - git:`git cat-file -p` 无大小限制(实测可读 GB 级文件,但 memory 占用等于文件大小)
   - 加软保护:`file_size > available_RAM/2` → skip + 警告,避免 OOM
   - 加上限感知日志:`已导入 N MB 文件,可用 RAM M MB`,给用户决策依据
3. **submodule**:**纳入**。逻辑跟普通文件一样走 git ls-tree + cat-file,只是 sidecar 里标 `submodule:true` + `src_submodule_path`。若 submodule 本身没版本管理(GitLink → 无 blob),skip + log
4. **M3.32 推进**:**M3.31 完成后直接推进 M3.32**(共享 snapshot 目录 + 跨进程 timeline merge),不停

### 12.1 增量决策(2026-09-16 续)

5. **git 缺失时启动探测**:
   - 启动 / 触发时探测 `git --version`,不在则:
     - 前端弹一次权限闸(类似「Prisir 想要读 git 历史」)
     - 内容:「本机未检测到 git 命令,启用外部版本管理兼容需要先安装(Windows: Git for Windows / macOS: `brew install git` / Linux: 包管理器安装)。是否打开下载页?」
     - 用户点「是」→ Tauri shell_open_external → https://git-scm.com/downloads
     - 用户点「否」→ 关闭弹窗 + 缓存 `git_available:false` 到 `_GIT_AVAILABLE`,所有相关功能走 no-op(扫描 worker 跳过、read_file hook 跳过、**不报错**)
   - 缓存失效:用户重启 PrisirAI / 用户手动触发「重检 git」设置项
   - **绝不静默下载 git** — 用户态杀毒规则不允许(参见[[ime-experience-to-security-tools-signing-2026-09-04]]);权限闸是教育和引导,不是强制

6. **运行时系统环境作为设计出发点**(详见 §15):
   - 不假设 git 在 PATH(80% Win 用户没装)
   - 不假设 Python(backend.exe 自带)
   - 不假设 ssh 配置(Win 10 1803+ 自带 OpenSSH client)
   - 不假设 NFS/SMB mount(M3.32 由用户自挂)
   - 不假设 fsync / flock 语义(Win 用 `msvcrt.locking`,Unix 用 `fcntl.flock`,封装成 `_file_lock(path)` 业务层不感知)

- §4.1 扫描:启动先 `_detect_git()`,若无 → 缓存 `git_available:false` + 弹权限闸一次;worker 走 no-op
- §4.2 读触发器:`_GIT_AVAILABLE:false` 直接 return
- §4.4 边界:submodule 改为纳入;新增「git 缺失」no-op 分支
- §4.5 sidecar:`submodule:true` 字段
- §4 新增 §4.6:`_file_lock(path)` 平台无关封装(M3.32 预热)

# 15. 运行时系统环境 — 设计出发点

## 15.1 目标用户设备画像

| 平台 | 默认有 `git`? | 默认有 Python? | PrisirAI 部署 |
|---|---|---|---|
| **Windows 10/11 用户(主流)** | ❌ 80% 没装 | ❌ | Tauri 装包 → `backend.exe`(PyInstaller) |
| **macOS 用户** | ❌ 默认无 | ❌ | 同上 Tauri 装包 |
| **Linux 用户(开发者)** | 部分 | 部分 | deb/rpm/AppImage |
| **服务器 / NAS** | ✅ | ✅ | docker / 直接 python |

## 15.2 关键约束

1. **gitpython 不进 backend.exe** — 子进程调 git 命令(5ms 开销可接受,exe 不增重)
2. **git 缺失时弹权限闸**而非 fail(80% Win 用户引导而非阻断)
3. **snapshot 目录可配置** — M3.32 走用户指定 mount 点
4. **不替用户挂载网络盘** — 网络错误/凭据/防火墙/提权都太复杂
5. **跨平台锁**:`_file_lock(path)` 封装,业务代码不感知平台

## 15.3 backend.exe 内部形态

```
PrisirAI-Setup-2.7.7.exe (NSIS)
  └─ C:\Users\<user>\AppData\Local\PrisirAI\
     ├─ backend.exe              # PyInstaller(包含 prisiragent_web.py + 依赖)
     ├─ frontend/                # Tauri webview 资源
     ├─ settings.db              # SQLite
     ├─ keys.db                  # SQLite (PrisirKeyStore)
     ├─ snapshots/               # 默认 snapshot 目录
     └─ settings.json            # 用户配置
```

读触发器 hook 在 backend.exe 里都是**纯 Python**,避开动态加载即可。
